# Хостинг и развертывание

## Хостинг бэкенда

### Обзор

Artube предоставляет полноценную Kubernetes инфраструктуру для развертывания серверных компонентов игр. Платформа автоматически управляет контейнерами, базами данных, масштабированием и мониторингом ваших бэкенд сервисов.

Конкретные требования к контейнеру и деплою бэкенда (Dockerfile в корне, экспонируемый порт, переменные окружения, `.gitlab-ci.yml` и `R2_GAME_ID`, health-пробы `/livez`/`/healthz`, формат логов) описаны на странице **[DevOps и деплой бэкенда](devops.md)**.

## Хостинг фронтенда

### Обзор

Artube предоставляет автоматизированное развертывание фронтенда игр через GitLab CI/CD пайплайн. Система принимает результат сборки (папку `dist`) и автоматически развертывает его в CDN для глобального доступа.

### Требования к проекту

#### Структура dist папки

Ваш проект должен генерировать папку `dist` с готовыми для продакшена файлами:

```plaintext
dist/
├── index.html          # Главная страница игры
├── assets/             # Результат работы бандлера
└── favicon.ico
```

#### Команда сборки

Проект должен иметь npm скрипт `build`, который создает оптимизированную папку `dist`:

```json
{
  "scripts": {
    "build": "vite build",
    // или
    "build": "webpack --mode=production",
    // или
    "build": "parcel build src/index.html"
  }
}
```

### GitLab CI/CD Pipeline

Файл GitLab пайплайна предоставляется командой Artube.

#### Этапы развертывания

1. **Build**

   - `npm ci` для воспроизводимых сборок
   - `npm run build` создает оптимизированную `dist/` папку
2. **Deploy**

   - содержимое `/dist` попадает в бакет
3. **Уведомления**

   - приходит уведомление в Slack канал (CDN требуется еще около минуты чтобы синхронизироваться, после чего можно играть)

### Безопасность

CSP на бакете выставляется так, что ассеты игры можно будет открыть только с домена прикрепленного к бакету, загрузить их откуда-то еще не получится.

#### HTTPS Everywhere

- **Forced HTTPS** - все соединения только через HTTPS
- **HSTS headers** - защита от downgrade атак
- **SSL certificates** - автоматическое управление сертификатами
- **Mixed content protection** - предотвращение смешанного контента

### Лучшие практики сборки

- Кладите всё в бандл: переводы, картинки, весь js код
- Если можете лениво подгружать код или ассеты после загрузки основного бандла — делайте это. Например, загружайте звуки позже

#### Версии

- Фронтенд версионируется согласно семверу

### Кэширование и cache busting

Важно

CDN отдаёт статические файлы из папки `dist` с заголовком `Cache-Control: public, max-age=31536000, immutable`. Это означает, что браузер и CDN-edge узлы **закэшируют файл на год** и не будут повторно проверять его изменения до истечения этого срока — даже если вы задеплоите новую версию игры под тем же именем файла.

**Следствие:** если ваш бандлер не изменяет имя файла при каждой сборке (например, всегда генерирует `index.js` вместо `index.a1b2c3.js`), игроки могут годами получать из кеша устаревшую версию кода, даже после успешного деплоя новой.

**Обязательное требование:** имена всех статических ассетов (JS, CSS, картинки, шрифты), включаемых через хэш содержимого в имя файла — так называемые **hashed/versioned filenames** (например, `main.[contenthash].js`, `styles.[contenthash].css`). Только `index.html` может (и должен) отдаваться без долгого кэширования, поскольку именно он ссылается на актуальные хэшированные имена ассетов при каждой сборке.

Большинство современных бандлеров включают content-hashing по умолчанию в production-режиме:

```json
{
  "scripts": {
    "build": "vite build"
  }
}
```

Vite, Webpack (в режиме `production` с `[contenthash]` в `output.filename`) и Parcel уже генерируют хэшированные имена файлов “из коробки” — дополнительная настройка обычно не требуется, если вы используете стандартную production-сборку без кастомизации имён выходных файлов.

> Осторожно
>
> Если игра переопределяет имена выходных файлов бандлера (убирая хэш), при следующем деплое CDN продолжит отдавать закэшированную версию игрокам, у которых уже был открыт клиент — обновление UI/логики игры будет недоступно до истечения годового `max-age` или ручной инвалидации кэша на стороне игрока (hard refresh).
