# Руководство по подключению API

## Обзор

Практическое руководство по подключению игрового бэкенда к Artube Games API, включая правила коннектов/реконнектов и обработку ошибок.

## Сценарии переподключения WebSocket

### Обзор сценариев восстановления соединения

Система Artube Games API поддерживает автоматическое восстановление соединений при различных типах сбоев. Ниже описаны основные сценарии и стратегии их обработки.

### 1. Потеря соединения между Game Server и Artube Games API

**Причины:**

- Перезапуск пода Artube Games API
- Сетевой сбой
- Перегрузка системы
- Превышение времени ожидания (idle timeout)

**Симптомы:**

- Запросы [`OpenRoundRequest`](../../games-api-integration/game-requests/open-round.md) и [`CloseRoundRequest`](../../games-api-integration/game-requests/close-round.md) остаются без ответа
- Клиент находится в состоянии ожидания

**Действия Game Server:**

1. **Обнаружение разрыва:** Game Server должен обрабатывать события `onclose`/`onerror` WebSocket
2. **Автоматическое переподключение:** Инициировать переподключение с экспоненциальной задержкой
3. **Блокировка запросов:** Пока соединения нет, все входящие от клиентов запросы должны немедленно завершаться с ошибкой `InternalServerError`
4. **Восстановление состояния:** Когда клиент повторно подключается (даже со старой сессией), необходимо запросить состояние заново, как при первичном подключении

**Heartbeat мониторинг:**

- Запросы каждые 15 секунд для раннего обнаружения разрыва
- Соответствует стандарту RFC 6455

```typescript
// Пример реализации reconnect логики
class GameServerConnector {
  private reconnectAttempts = 0
  private readonly maxReconnectAttempts = 5
  private readonly baseDelay = 1000 // 1 секунда

  private async reconnect(): Promise<void> {
    if (this.reconnectAttempts >= this.maxReconnectAttempts) {
      throw new Error('Максимальное количество попыток переподключения превышено')
    }

    const delay = this.baseDelay * Math.pow(2, this.reconnectAttempts)
    await new Promise(resolve => setTimeout(resolve, delay))

    try {
      await this.connect()
      this.reconnectAttempts = 0
    } catch (error) {
      this.reconnectAttempts++
      await this.reconnect()
    }
  }

  private onConnectionLost(): void {
    // Блокировка всех новых запросов
    this.blockIncomingRequests = true

    // Запуск процесса переподключения
    this.reconnect().catch(error => {
      console.error('Критическая ошибка переподключения:', error)
    })
  }
}
```

### 2. Перезапуск пода Game Server

**Причины:**

- Деплой новой версии
- Падение процесса
- Out-of-memory ошибки
- Вытеснение узла

**Симптомы:**

- Клиентские WebSocket-сессии прерываются

**Действия:**

1. **Новые подключения:** При старте игровой сервер получает новые подключения от игроков
2. **Восстановление состояния:** Сервер работает так, будто ничего не прерывалось, восстанавливая клиентов в нужное состояние на основе информации о раунде
3. **Обработка ошибок клиентов:** Клиенты получают ошибку о невозможности достучаться до сервера
4. **Стратегия переподключения:** Механизм переподключения игровых клиентов к игровым серверам определяется командой разработки игры

### 3. Перезапуск пода Artube Games API

**Симптомы и действия:** Аналогично сценарию #1 (потеря соединения между Game Server и Artube Games API)

**Дополнительные меры:**

- Все активные сессии будут переустановлены
- Требуется полная реинициализация соединений
- Heartbeat механизм поможет быстро обнаружить недоступность API

### 4. Потеря соединения игрового клиента c игровым сервером

Ответственность игровой команды

Обработка данного сценария находится в зоне ответственности команды разработки игры. Рекомендуется реализовать:

- Автоматическое переподключение с экспоненциальной задержкой
- Сохранение состояния игры на стороне клиента
- Механизм восстановления незавершённых операций

### 5. Частичный сбой кластера

**Симптомы:**

- Часть подов теряет доступ к Artube Games API
- Поды остаются подключёнными к клиентам
- Нулевой SLA индикатор показывает инцидент

**Действия:** Аналогично сценарию #1

**Мониторинг:**

- Система мониторинга автоматически обнаружит проблему через SLA метрики
- При эскалации инцидента — передать команде Artube для ручного разбора

### Корнер-кейсы

Ручная обработка

Нестандартные сценарии и корнер-кейсы разбираются вручную командой Artube. При возникновении таких ситуаций обращайтесь в техническую поддержку с детальным описанием проблемы.

## Рекомендации по использованию

### Обязательные требования

- **Не обрывайте WebSocket-соединение принудительно** — при потере соединения инициируйте переподключение, не закрывайте соединение со стороны клиента; соединение закрывается только по сигналу сервера ([`GoAway`](../../games-api-integration/control-requests/goaway.md))
- **Всегда обрабатывайте сообщение `GoAway`** для корректного завершения работы
- **Используйте `corr_id`** для связи запросов и ответов
- **`round_state` должен быть JSON-строкой**, а не объектом
- **Валидируйте все ответы** перед их обработкой

### Лучшие практики

- **Реализуйте надёжное переподключение:** Используйте экспоненциальную задержку и ограничение попыток
- **Heartbeat мониторинг:** Ping/pong каждые 15 секунд для раннего обнаружения разрывов соединения
- **Блокировка при отсутствии API:** Все запросы должны завершаться с ошибкой `InternalServerError`, если нет соединения с Artube Games API
- **Восстановление состояния:** При переподключении всегда запрашивайте актуальное состояние сессии
- Всегда проверяйте баланс после каждой операции с раундом
- Используйте соответствующий `round_state_version` для каждого обновления
- Логируйте все сообщения для отладки
- Реализуйте таймауты для всех запросов
- Обеспечьте корректное завершение работы при получении [`GoAway`](../../games-api-integration/control-requests/goaway.md)

### Безопасность

- Валидируйте все входящие данные
- Ограничивайте размер `round_state` разумными пределами
