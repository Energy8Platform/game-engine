# Scaffold polish + general spin-result coercion — Design (slice 9)

Date: 2026-06-23. Branch: `feat/game-spec-define-game` (continuing).

**Goal:** four scaffold/runtime improvements so a generated slot is more complete and robust: (1) a `postbuild` zip step, (2) a real game-owned `IntroScene` (not just logo + tap), (3) a `build:stake` build target, and (4) — the spine — a **general spin-result schema/coercion** applied to ALL games (today stake-only), which also fixes a live crash where a Lua empty table `{}` reaches `(x ?? []).map`.

**Decisions (from brainstorming):**
- **#4 coercion:** a general **zod schema** generated for every game (not stake-only). Array fields coerce `{}`→`[]` structurally via a shared `luaArray` helper, so the crash is impossible by construction. `normalize` and the stake adapter both derive from the one schema.
- **#2 intro:** the scaffold **generates a game-owned `IntroScene` subclass**; the host's `intro` option gains the ability to accept a custom `Scene` class (the existing config path stays for `spec-slot`/back-compat).
- **#1 postbuild / #3 build:stake:** the kitsune patterns, generated by the scaffold.

## Motivation

A user ran a scaffolded game and hit `normalize.ts:25 Uncaught TypeError: (d.cascades ?? []).map is not a function`. Root cause: fengari decodes an empty Lua table as a JS object `{}`, and `?? []` does not catch `{}` (it is not nullish), so `{}.map` throws. The codegen `normalize` template ([create-slot/src/codegen/normalize.ts](../../../packages/create-slot/src/codegen/normalize.ts)) emits this `?? []` idiom for every array field, so every scaffolded cascade game is exposed. `slot-result` already ships `asArray()`/`coerceLuaArrays()` that handle `{}`, but the template doesn't use them, and the only schema-based validation today is the **stake-only** `spinSchema` in [stakeAdapter.ts](../../../packages/create-slot/src/codegen/stakeAdapter.ts). The fix generalizes that schema to all games. Alongside, three scaffold-completeness gaps (no `postbuild` zip, a stub intro, no `build:stake`) match what shipped games (kitsune) actually need.

## Design principle

One generated `schema.ts` (zod) is the single source of a game's **raw** spin-result shape, with `{}`→`[]` coercion built in. `normalize` parses the raw result through it; the stake adapter reuses it. No result-shape fact is written twice, and the `{}` crash is structurally impossible.

## Piece 1 — `postbuild` zip (#1)

[create-slot/src/codegen/packageJson.ts](../../../packages/create-slot/src/codegen/packageJson.ts) `genPackageJson` adds, after `build`:
```jsonc
"postbuild": "rm -f <id>.zip && cd dist && zip -r ../<id>.zip ."
```
The zip is named after the game id (`a.id`). `npm run build` runs `vite build` then npm's lifecycle fires `postbuild`, producing `<id>.zip` at the project root. Unconditional (every game).

## Piece 2 — `build:stake` target (#3)

For stake games (`a.stake`) only:
- `genPackageJson` scripts:
  ```jsonc
  "dev:stake":   "BUILD_TARGET=stake vite",
  "build:stake": "BUILD_TARGET=stake vite build",
  "stake:bundle": "rm -rf dist-stake stake-math <id>-stake.zip stake-math.zip && npm run build:stake && npm run math && cd dist-stake && zip -r ../<id>-stake.zip . && cd ../stake-math && zip -r ../stake-math.zip . && cd .. && echo 'Stake artifacts: <id>-stake.zip + stake-math.zip'"
  ```
- The template [vite.config.ts](../../../packages/create-slot/template/vite.config.ts) branches on `process.env.BUILD_TARGET === 'stake'`:
  - **stake:** `devBridge: false`, `vite: { build: { outDir: 'dist-stake' } }`.
  - **default:** current (devBridge on, `dist/`).

The same `main.ts` serves both targets — `createSlotGame` detects a stake launch at runtime via `isStakeLaunch` and activates the bridge. `build:stake` differs only in plugins (no devBridge) and output dir. Non-stake games omit these scripts and the `vite.config` branch is inert (env never set).

## Piece 3 — game-owned `IntroScene` (#2)

**Host** ([game-engine/src/host/createSlotGame.ts](../../../packages/game-engine/src/host/createSlotGame.ts) + `types.ts`): `CreateSlotGameOptions.intro` becomes a union:
```ts
intro?: IntroSceneConfig | { scene: SceneCtor; data?: unknown };
```
- Config form (existing): registers the built-in `IntroScene` with the config — unchanged, keeps `spec-slot` working.
- Class form (new): registers the provided `Scene` constructor as `__intro__` and starts it with `{ ...data, onStart }`, where `onStart` does `game.scenes.goto(gameKey)` (same wiring as today). The intro→game `bindGameScene` flow is unchanged.

`SceneCtor` = the constructor type the scene manager already accepts (`new () => Scene`). The discriminant is the presence of a `scene` property.

**Scaffold:** a new codegen `genIntroScene` emits `src/scenes/IntroScene.ts` — a real `Scene` subclass with a richer starter the author edits: a background (Graphics fill or texture slot), the game title from the spec, a subtitle line, a styled **PLAY** start button (the engine UI `Button`) that calls the host-injected `onStart`, and a fade-in `Tween` on enter. `main.ts` wires `intro: { scene: IntroScene }`. The game-engine built-in `IntroScene` primitive stays for the config path.

## Piece 4 — general spin schema + coercion (#4, the spine)

**Reuse existing infra — no new helper.** `@energy8platform/stake-kit` already exports the exact schema-driven Lua-array coercion the stake adapter uses: `deriveArrayFields(schema)` (walks a zod schema for array-field names, at any depth — [schema.ts](../../../packages/stake-kit/src/schema.ts)) and `coerceLuaArrays(data, fieldSet)` (recursively replaces `{}`→`[]` for those keys at any depth — [book.ts](../../../packages/stake-kit/src/book.ts)). `createGameAdapter` already does `coerceLuaArrays(payload, deriveArrayFields(schema))` then a lenient `schema.safeParse`. The general fix applies the same two exports to the non-stake `normalize` path — both already shipped and tested; the schema is the single source of the array-field list.

**Generated `src/game/schema.ts`** (for ALL games, not just stake) — the single source of the **raw** Lua spin-result shape, using plain `z.array(...)` (no special wrapper — `deriveArrayFields` finds them):
```ts
import { z } from 'zod';

export const spinSchema = z.object({
  totalWin: z.number().optional(),
  data: z.object({
    cascades: z.array(z.object({}).passthrough()).optional(),
    multiplier: z.number().optional(),
    free_spins: z.object({ awarded: z.number(), total: z.number() }).optional(),
  }).partial().optional(),
});
export type RawSpin = z.infer<typeof spinSchema>;
```
(Reel-spin games use a `matrix: z.array(z.array(z.number()))` field instead of `cascades`.)

**Generated `normalize.ts`** derives the array-field set ONCE at module load (mirrors `createGameAdapter`), coerces every raw result through it, leniently validates, then maps to the scene-facing `SpinData`:
```ts
import { deriveArrayFields, coerceLuaArrays } from '@energy8platform/stake-kit';
import { spinSchema, type RawSpin } from './schema';

const arrayFields = deriveArrayFields(spinSchema);   // once

export const normalize: SlotResultNormalizer<SpinData> = (raw) => {
  const coerced = coerceLuaArrays((raw ?? {}) as Record<string, unknown>, arrayFields);
  const parsed = spinSchema.safeParse(coerced);
  const d = (parsed.success ? parsed.data : coerced) as RawSpin;   // lenient — never throws
  return {
    totalWin: d.totalWin ?? 0,
    freeSpins: d.data?.free_spins ? { awarded: d.data.free_spins.awarded, total: d.data.free_spins.total } : undefined,
    steps: (d.data?.cascades ?? []).map(...),        // cascades is now ALWAYS a real array (was {})
    ...
  };
};
```
The `?? []`/`.map` crash is gone structurally: `coerceLuaArrays` turned the Lua `{}` at `data.cascades` into `[]` before the `.map`.

**Stake adapter** (when `a.stake`): imports the SAME `spinSchema`/`RawSpin` from `../game/schema` instead of declaring its own. The `genStakeAdapter` schema half is removed; `createGameAdapter({ schema: spinSchema, ... })` already runs the identical coercion.

**Dependency:** `zod` moves from a stake-only dep to a universal scaffold dependency (`genPackageJson` always includes it). The general schema lives at `src/game/schema.ts` for ALL games; the stake adapter (`src/stake/adapter.ts`) imports `../game/schema`. No more `src/stake/schema.ts`.

**spec-slot** (living proof): adopts a `schema.ts` + schema-based `normalize` (and optionally the intro subclass) so the example demonstrates the new flow and a regression test can lean on it.

## Testing

- **stake-kit:** `luaArray` coerces `{}`→`[]`, passes a real array through, drops non-array scalars to `[]`; the inner item schema still validates array elements.
- **game-engine host:** `intro` option resolution — the class form registers the custom scene and wires `onStart`; the config form still uses the built-in `IntroScene` (resolved without Pixi where unit-testable; Pixi parts via typecheck).
- **create-slot:** `genSchema` emits a zod schema using `luaArray` for the array field; `genNormalize` emits schema-based parsing with no `?? []`; the **regression test** — a generated normalize fed a raw result whose array field is `{}` returns `[]` and does not throw; `genStakeAdapter` imports `./schema` and declares no own schema; `genPackageJson` emits `postbuild`, `build:stake`/`dev:stake`/`stake:bundle` (stake games), universal `zod`; `genIntroScene` emits a `Scene` subclass with `onStart`; `main.ts` wires `intro: { scene }`. The anti-drift scaffold smoke stays green (the generated `schema.ts`/`IntroScene.ts` typecheck against real packages).
- **Proof:** `examples/spec-slot` regenerated/updated to the schema + intro flow, verified by tsc + smoke; the regression test proves a `{}` array no longer crashes normalize.

## Out of scope (YAGNI / separate slice)

- Migrating existing bespoke games' normalizers (they own their code).
- A non-zod coercion path (the decision is a universal zod schema).
- Richer intro animation libraries — the generated intro uses the engine's own `Tween`.
- Enriching the game-engine built-in `IntroScene` primitive (the scaffold owns its intro subclass; the primitive stays minimal for the config path).

## Risks / open items

- **zod as a universal dep:** every scaffolded game gains zod. Accepted (small, well-established; unifies stake + non-stake; structural coercion). The anti-drift smoke must `file:`-link or resolve zod (it's a published dep, so `npm install` fetches it).
- **Schema validation throwing:** resolved — `normalize` uses `safeParse` and falls back to the coerced object on failure (mirrors `createGameAdapter`), so it never throws on a shape mismatch; coercion has already fixed the `{}`→`[]` case regardless.
- **`SceneCtor` type:** must match what `SceneManager.register` accepts; verify the exact constructor signature when wiring the union (no-arg `new () => Scene`).
- **build:stake output dir vs defineGameConfig:** confirm `defineGameConfig` forwards `vite.build.outDir` (it passes a `vite` block through); if not, set `build.outDir` via the raw vite option it exposes.
