# Игровые строки редактируются, горячий форк — дизайн

Дата: 2026-09-16. Ветка `feat/slot-webide-cordis`, от `0e1739f`.
Родительская спека: `2026-08-27-slot-webide-cordis-design.md` — §2 («горячий
форк с откатом на перезагрузку: плагин объявляет `hot`, поля схемы —
`applies: 'restart'`»), §5.3 («хост по каждой правке знает, перезапустить
форк или перезагрузить iframe, и показывает это до того, как крутанули
ручку»), §5 экран «Состав» («у каждой ручки видно, горячая она или требует
перезапуска»), §10 п.2 («не открыв ни одного файла — выключить reel-фичу,
поменять её настройки … и увидеть в превью; где правка горячая, сессия и
баланс не теряются»). Пользователь выбрал «одним срезом».

## 1. Зачем (измерено)

- Экран Composition показывает строки **игры** (`renderer1`, `stage1`,
  `reels1`, `mechanics1`…) как имя и слой: рантайм-пакеты не объявляют
  схему, хост не отдаёт её, писать в `e8.patch.yml` из IDE нечем. Мышью
  правятся только строки **IDE** (`e8.yml`: `bridge1`, probe).
- Игра по `/ide` получает снимок IDE-композиции; живой перебинд есть только
  у `ide-bridge` (механика стадии). Правка игровой строки доходит до игры
  лишь перезагрузкой iframe — и только если что-то перечитало патч.
- Все рантайм-строки объявлены `hot: false`; `createGame` применяет строки
  один раз и fiber'ы не хранит; cordis `Fiber.update(config)` существует.
- Главный вход рантайм-пакетов (`reels`, `stage`, `renderer-pixi`) тянет
  `pixi.js` — хост не может импортировать его ради схемы.

§10 п.2 по игровым строкам не выполнен. Срез его выполняет.

## 2. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где схема рантайм-строки | Пакет объявляет `e8.runtime.schema: './src/schema.ts'` — модуль **только** со `schemastery` (`export const Config`), без pixi; хост импортирует этот файл (tsx) и кладёт `schema` (`Config.toJSON()`) и `hot` в `GameCompositionRow` | Клиентские половинки уже так делают (`Config` экспорт); отдельный файл — потому что главный вход не годится для node |
| Кто получает схемы | `reels` (то, что правит патч: `config.{reels,rows,…}` — измерить в плане, минимум поля патча `first-slot`), `renderer-pixi` (`width`, `height`, `background`), `stage` (`design.width/height`), `game-runtime` (`mechanics1`: `stages: dict(string)`) | Четыре строки патча эталонного проекта |
| Горячесть | Манифест `hot` + поле `applies: 'restart'` в схеме. `mechanics1` — hot (перебинд, как `ide-bridge`); `reels1` — hot (пересборка барабана по `fiber.update`); `renderer1`, `stage1` — cold (`hot: false`) | Горячее там, где повторный `apply` строки восстанавливает картину; холст и размер сцены — перезагрузка честнее |
| Правка | Composition рисует `SchemaForm` для игровой строки (тот же компонент, тот же бейдж `restart`); `onChange` → `PUT /api/composition/rows/:id { config }` | Один рендерер форм на оба состава |
| Запись | Хост: `project.writePatchRow(id, config)` — `e8.patch.yml` читается `js-yaml`, строка с `id` получает `config` **целиком** (семантика патча — замена), вставляется в конец, если её не было; `yaml.dump`; комментарии файла не сохраняются (как у `e8.yml`, записано) | Патч — единственное место, где IDE владеет составом игры (§3 родительской) |
| После записи | `project.reload()`, `spinSchema.reload()`; хост вычисляет `reload: boolean` = строка `hot: false` **или** среди изменившихся полей есть `applies: 'restart'` (по схеме, по путям верхнего уровня); ответ `PUT` = `{ rows, reload, diagnostics }`; кадр `{ type: 'game-composition', rows, reload, changed: [id] }` всем `/ide`-сокетам (корень и превью) | Решение hot/cold — на хосте, по данным; клиент и игра только исполняют |
| Клиент | `gameComposition` получает свой `/ide`-сокет (паттерн), обновляет `rows` по кадру; `PreviewWall` перезагружает iframe по `reload: true` (вместо `coldSignature`), не трогает при `false` | Один источник решения |
| Игра | `createGame` хранит `Map<rowId, Fiber>`, предоставляет `gameRows: { update(id, config): 'updated' \| 'unknown' }` → `fiber.update(config)`; `ide-bridge` слушает `game-composition` с `reload: false` и вызывает `update` для `changed`; при `reload: true` ничего не делает (iframe перезагрузит IDE) | Форк — это fiber строки; cordis сам снимает эффекты и применяет заново |
| `reels1` горячая | Повторный `apply` создаёт новый `board`, старый `destroy` через эффект; `play-loop` (`requires: ['board']`) должен читать `ctx.board` **при каждом спине**, не захватывать при `apply` — измерить в плане (спайк, первая задача); если захватывает — поправить чтение на ленивое | Иначе горячая правка барабана оставит петлю на мёртвом объекте |
| Сессия и баланс | Не перезагружать страницу — значит `spinlog1`, `session`, `#log` живут; e2e проверяет счётчик записей лога до/после горячей правки и отсутствие remount iframe | §10 п.2 буквально |
| Вне | Удаление/добавление строк из IDE (только правка конфига существующих); `e8.profile.yml`; сохранение комментариев патча; горячие `renderer`/`stage`; правка `.spin` (перезапуск `e8-server` — уже есть) | Следующие срезы |

## 3. Провод

```
GET  /api/composition                 → { rows: GameCompositionRow[] (+schema, hot), diagnostics, schema }   (как сейчас + два поля)
PUT  /api/composition/rows/:id        { config } → 200 { rows, reload, diagnostics } | 400 (нет такой строки / тело) | 500 (запись)
ws   ServerMessage += { type: 'game-composition'; rows; reload: boolean; changed: string[] }
```

`GameCompositionRow += { schema: unknown | null; hot: boolean }`;
`E8RuntimeHalf += { schema?: string }`.

## 4. Отказ — это данные

- Схема не импортируется (нет файла, бросил) → `schema: null` + диагностика
  строки (как у клиентских половинок); форма не рисуется, строка остаётся.
- `PUT` неизвестного `id` → 400; патч не читается/не пишется → 500 с
  диагностикой, файл не тронут (запись во временный файл + `rename`).
- `fiber.update` бросил в игре → диагностика в `ctx.diagnostics` игры
  (доходит до панели через `ide-bridge`), строка остаётся на старом конфиге
  — cordis не откатывает; `reload` не форсируется.
- Кадр с `changed` для строки без fiber'а (не применялась — проиграла шов)
  → `'unknown'`, без диагностики.

## 5. Проверка

Юниты: контракты; `runtime-assets` — схема с `./schema`, `hot`, `null` при
ошибке; `project.writePatchRow` — замена/вставка, атомарность, диагностика;
`reload` — три случая (cold-строка; hot-строка без restart-полей; hot-строка
с изменённым restart-полем); `rpc` — кадр всем сокетам; клиент —
`gameComposition` по кадру, `PreviewWall` по `reload`; форма игровой строки
с бейджем; игра — `gameRows.update` зовёт `fiber.update`, `'unknown'`;
`ide-bridge` — кадр → `update` по `changed`, `reload: true` — ничего;
`reels` — второй `apply` даёт новый `board`, старый уничтожен; `play-loop`
читает `board` лениво (спайк).

Playwright (`hot-fork.spec.ts`): (1) в Composition у `reels1` есть форма,
у `renderer1` — поля с бейджем `restart`; (2) спин → лог игры N записей →
изменить поле `reels1` → iframe **тот же** (`__e8` id страницы не сменился /
`iframe` element identity), лог по-прежнему N, следующий спин — N+1, и
барабан отражает правку (RPC `window.__e8`: измерить, что доступно, напр.
число барабанов); (3) изменить `renderer1.width` → iframe перезагружен,
`#status` снова `ready`; (4) `e8.patch.yml` на диске содержит новое значение;
(5) `bridge1` по-прежнему перебиндивает механику (регрессия). Полная сюита.

## 6. Риски

| Риск | Что делаем |
|---|---|
| `play-loop`/`stage` держат ссылку на `board` | Спайк первой задачей; ленивое чтение или `hot: false` у `reels1` с записью |
| `yaml.dump` теряет комментарии `e8.patch.yml` эталона | Комментарии эталона переносятся в `docs/` / README проекта; записано как решение |
| Схема `reels` велика (`CreateReelSystemOptions`) | Схема покрывает поля патча `first-slot`; остальное `Schema.any()` с пометкой |
| Две правки подряд до `reload()` | `PUT` сериализован на хосте (цепочка), как `workspace` |
