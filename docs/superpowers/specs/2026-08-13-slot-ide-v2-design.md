# Slot IDE v2 — плагинное ядро и среда авторинга

**Дата:** 2026-08-13
**Статус:** дизайн согласован, ждёт плана реализации
**Область этой спеки:** Срез 0 (вертикальный прорез через M1–M4). M5–M8 — отдельными спеками.

---

## 1. Зачем

Первый заход на WebIDE (ветка `feat/slot-ide-ir`, ~450 тестов, scene-IR + flow-IR + гизмо +
панель ассетов + mode-оверлеи) был отклонён по итогам двух ревью: «не тянет на нано-IDE» и
«этим невозможно пользоваться». Диагноз пользователя — две корневые причины:

1. **Фреймворк не плагинный.** Reel-фичи — закрытая запись `FEATURES: Record<FeatureKey,
   ReelFeature>`; `createSlotGame` — 917 строк с именованными ветками `stake`/`artube`/`shell`/
   `loading`. Пока состав игры зашит в код, требование «всё настраивается через UI» невыполнимо
   в принципе.
2. **Редактор был отладчиком.** Аутлайнер и инспектор поверх iframe — это devtools-панель, а не
   среда, в которой делают игру.

Модель IR (интерпретируемые `scene.json` / `flow.json`) под критику **не попала** — она
остаётся допустимой. Но продукт проектируется с чистого листа; движковые куски v1 подбираются
только там, где совпадут сами собой.

### Что изменилось в репозитории с момента v1

- **SpinML вытеснил Lua** (`docs/spinml.md`). `.spin` — статически типизированный DSL,
  JIT-компилируемый в нативный код. Ключевое для нас: `enum SpinData tag stage { … }` — это
  **типизированная схема результата спина**, а `action` с `opens`/`extends`/`ends when` —
  декларативное описание режимов игры. Требование «schema first» больше не надо изобретать:
  SSOT уже существует и уже проверяется компилятором.
- `@energy8platform/harness` обзавёлся настоящей плагинной моделью (backend + panel) — это
  живой прецедент для контрибуций и для разделения фаз.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Диагноз v1 | Непагинный фреймворк + редактор-как-отладчик. Причины не разбираем дальше, продукт — с чистого листа. |
| SSOT проекта | **Диск**, но **проектом владеет IDE**: она его создаёт, диктует структуру и является единственным редактором документов. |
| Совместимость | **Разрыв** (новый мажор). Старое — legacy. Обязательство: одну реальную игру переносим целиком как make-or-break. |
| Аудитория | Внутренняя сейчас; контракты, манифесты и версионирование делаются **публично-пригодными сразу**, инфраструктура маркетплейса — нет. |
| Модель плагина | **C — открытый реестр контрибуций + объявленные хуки.** |
| Порядок работ | **Вертикальный срез** (тонкие M1+M2+M3+M4), затем углубление. |
| Игра-эталон | **Копия `moon-spice-market`** (framework-native, 3778 LOC, SpinML, stake-таргет). Оригинал read-only. Игру НЕ переписываем — она должна просто загрузиться и играться. |
| Именование | Новый мажор живёт под скоупом **`@energy8engine/*`**. `@energy8platform/*` остаётся legacy. |
| Стек IDE | React + Vite + Monaco (ради React Flow под M6). Зависимости остаются в IDE и никогда не попадают в игры. |

## 3. Центральная идея

**Единственный способ расширить систему — schema'д-контрибуция.** Плагин не «делает что-то»,
он **объявляет**: `{ точка расширения, id, схема настроек, ленивая фабрика, документация }`.
Схема **обязательна**: без схемы контрибуция не регистрируется.

Отсюда всё остальное получается бесплатно:

- **IDE рисует настройки сама** из схемы — ни одной захардкоженной панели, ни одного
  JSON-редактора;
- **ИИ-агент** читает те же схемы как документацию — отдельный слой доков не нужен;
- **маркетплейсу** есть что индексировать и валидировать;
- собственные части фреймворка (shell, loader, reels, таргеты) проходят **через ту же дверь** —
  догфудинг становится структурным свойством, а не обещанием.

Побочный эффект, ради которого это и делается: **IDE остаётся маленькой**. Бесспорных
собственных экранов в ней ровно три — сцена, flow, анимация. Всё прочее генерируется из схем,
и каждый новый плагин получает UI даром.

**Срез 0 = тонкие M1+M2+M3+M4.** M4 — точка, где решается судьба проекта: именно там v1
провалилась, имея глубокий движковый слой и слабый продукт. Поэтому сначала прорезаем насквозь
и смотрим глазами, и только потом углубляем.

### Пункты, добавленные к исходному запросу

1. **Математика внутри IDE** — `.spin`, симуляция, RTP/волатильность/max-win, books и curate.
   Без неё IDE делает половину игры, а `.spin` — та самая схема, на которой всё держится.
   (Срез 0: только редактирование `.spin` и `e8 check`; пайплайн — отдельной спекой.)
2. **Публикация как первоклассная операция** — stake-бандл и artube-деплой из IDE с
   преполётными проверками. Таргет и так становится плагином.
3. **Lock-файл плагинов** — без него ни маркетплейс, ни воспроизводимая сборка невозможны.
4. **Звук как первый класс** — каналы и декларативный дакинг. Ни в одной из 8 разобранных игр
   этого не было, все делали руками. (Не в Срезе 0.)
5. **Headless-петля проверки** — скриншоты и ассерты без браузера. Это фундамент для «ИИ-агент
   дебажит со скриншотами» и единственный надёжный способ проверять анимацию.

## 5. §1 — Ядро: `@energy8engine/kernel`

Новый пакет, renderer-agnostic: ни pixi, ни DOM, ни SDK. Знает только механику расширения.

### 5.1 Типы

```ts
// Манифест — БЕЗ побочных эффектов и тяжёлых импортов. Читается в Node без запуска игры.
interface PluginManifest {
  id: string                                   // '@e8/reel-system' | 'acme-cascading-wild'
  version: string                              // semver
  engine: string                               // требуемый диапазон версий ядра
  dependsOn?: Record<string, string>           // id → semver-range
  points?: Record<PointId, PointDef>            // объявляет НОВЫЕ точки расширения
  contributes?: Record<PointId, Contribution[]>
  hooks?: HookId[]                              // явный escape-hatch, из закрытого списка ядра
  settings?: Schema                             // настройки самого плагина
}

interface PointDef {
  phase: 'runtime' | 'build' | 'editor'  // точка принадлежит РОВНО одной фазе
  arity: 'one' | 'many'                  // 'one' → ui.shell; 'many' → reel.feature
  schema: Schema                         // схема настроек ЛЮБОЙ контрибуции сюда
  doc: string                            // agentDoc = документация в IDE = промпт агенту
}

interface Contribution {
  id: string
  schema?: Schema                        // СВОИ поля сверх схемы точки
  defaults?: unknown
  activateWhen?: Matcher                 // для точек arity:'one' с несколькими кандидатами
  create: () => Promise<Factory>         // ленивая загрузка рантайма
  doc: string
}
```

### 5.2 Решения, зашитые в эти типы

**(1) Эффективная схема = схема точки + схема контрибуции.** Точка `reel.feature` задаёт общее
(`enabled`, `priority`), контрибуция `expandingWild` добавляет своё (`direction`, `holdSpins`).
IDE рисует объединение. Общие поля никто не переписывает.

**(2) Схема — своя, доменная, а не JSON Schema.** Виды полей: `number(min,max,step)`, `text`,
`boolean`, `color`, `enum`, `asset`, `symbol`, `spinPath`, `nodeRef`, `sound`, `object`, `list`.
Доменные виды дают *хороший* контрол вместо generic-формы: `asset` — пикер ассетов, `symbol` —
список символов из спеки, `spinPath` — пикер по схеме спина. Это и есть разница между «всё
настраивается через UI» и «форма из пятнадцати текстовых полей». Конвертация в JSON Schema —
позже, для маркетплейса и агента.

**(3) Резолюция происходит до запуска и сериализуема.** `project.json` → манифесты → проверка
`engine`/`dependsOn` → топологическая сортировка (цикл = ошибка) → реестр точек и контрибуций,
каждая валидируется схемой своей точки. Результат — **`ResolvedPlan`**, обычные данные. Его
читают все трое: игра, IDE и агент. `create()` вызывается лениво, уже после.

**(4) Точка принадлежит одной фазе.** Stake нужен и на сборке, и в рантайме — значит он
контрибуцирует в две точки: `build.target` и `session.provider`. Так фазы не протекают.

**(5) Ошибки — данные, а не исключения.** Резолюция возвращает `{ plan, diagnostics[] }`, где
диагностика — `{ severity, pluginId, pointId, message, fix? }`. Прямой урок v1, где отказы
патчей молча терялись. На `warning` игра стартует деградировав; на `error` показывает
человеческий экран с текстом, а не белый прямоугольник. IDE показывает тот же список.

**Настройки лежат в проекте, не в плагине** — `project.json` хранит значения по схемам. Именно
этот файл пишет IDE, когда пользователь крутит ручки.

**Хуки закрыты и малочисленны**: `bootstrap`, `dispose`, `beforeSpin`, `afterSpin`,
`beforeRender`. Открытые хуки = хаос без интроспекции; узкий чёрный ход лучше широкого.
Плагин **обязан объявить** используемые хуки в манифесте — иначе IDE не знает, что в системе
есть непрозрачное поведение, и от кого.

### 5.3 Правило, которое всё держит

> Что IDE должна **настраивать** — живёт в schema'д-контрибуции.
> Что IDE достаточно **знать** — живёт в объявленном хуке.

## 6. §2 — Проект на диске и схема спина

### 6.1 Структура проекта

```
my-slot/
├── project.json          ← состав плагинов + все их настройки          [IDE]
├── project.lock.json     ← разрешённые версии плагинов                  [IDE]
├── game/
│   ├── script.spin       ← математика                                  [РУКАМИ]
│   └── spec.json         ← символы, паутаблица, бет-левелы, max win     [IDE, редактор позже]
├── scenes/*.scene.json   ←                                              [IDE]
├── flow.json             ← один файл на игру                            [IDE]
├── anim/*.anim.json      ←                                              [IDE]
├── plugins/<name>/       ← локальные плагины проекта                   [РУКАМИ]
├── assets/               ← дерево ассетов                               [IDE]
└── .e8/                  ← производное: кэш схем, скриншоты, отчёты sim
```

**Правило владения, буквально: руками правятся ровно две вещи — `game/script.spin` и
`plugins/**`.** Всё остальное пишет IDE. Это и есть «IDE владеет проектом» при SSOT на диске.

**`game.spec.ts` становится `game/spec.json`.** Сейчас паутаблица лежит в TS, а `.spin`
получает из неё пролог (`SPEC.*`, `PAY_H1`, `SYM.*`). Если паутаблицу редактирует IDE —
таблицей, а не текстом — она обязана быть данными. Генератор пролога читает JSON вместо TS;
типобезопасность не теряется, потому что `e8 check` всё равно проверяет пролог при компиляции.

**В Срезе 0 `spec.json` только читается** (генератором пролога и пикером `symbol`). Табличный
редактор паутаблицы — отдельной спекой вместе с математической панелью; конвертация
`game.spec.ts` → `spec.json` для игры-эталона делается один раз при переносе.

### 6.2 Схема спина

Парсер декларативной секции `.spin` разбирает `game {}`, `action {}`, `record {}`,
`enum … tag stage {}` — блоки с фиксированным синтаксисом, исполнять ничего не нужно:

```ts
interface SpinSchema {
  gameId: string;  betLevels: number[];  maxWin: number
  vars: RecordShape;  globals?: RecordShape
  stages: Record<string, RecordShape>   // из enum SpinData tag stage
  actions: ActionDef[]                  // stage, cost, session, opens, extends, endsWhen, feature{}
}
```

Отсюда IDE получает то, что иначе пришлось бы описывать второй раз:

- **режимы игры** — это `stage`-варианты;
- **как режимы открываются и закрываются** — из `opens` / `extends` / `ends when`;
- **пикеры `spinPath`** — все пути внутри данных стадии (`grid`, `grid[][].sym`,
  `scatter_count`): питание для flow-редактора и биндингов сцены;
- **валидацию до запуска** — биндинг на несуществующее поле становится ошибкой в редакторе.

Схему не мы придумали — её объявила математика, и `e8` её уже типизировал.

**Путь развития:** позже заменить парсер на `e8 --emit-schema`, когда дойдут руки до движка
(исходники в приватном `casino-platform/e8/`). Парсер в этом репо — чтобы не блокироваться.

### 6.3 Режимы и сцены

Режим игры **может быть отдельной сценой**: `project.json` связывает стадию со сценой
(`free_spins → scenes/fs.scene.json`). Чтобы это не превращалось в копипасту (типовой фриспин —
та же доска, перекрашенная), у сцены есть **`extends`**: сцена фриспинов наследует базовую и
хранит только дельту. Реально другой экран — сцена без `extends`. Одна механика покрывает оба
случая; композиция сцен закрывает дыру, из-за которой v1 не могла этого сделать вовсе.

**В Срез 0 входит:** `project.json` + lock + парсер `.spin` + `SpinSchema`. Редакторы сцен и
flow — следующими спеками; файлы просто объявлены в формате.

## 7. §3 — Разрез фреймворка на плагины

**Разрыв проходит по слою композиции, а не по реализациям.** `shell`, `/slot`, `platform-core`,
`stake-bridge`, `artube-bridge` не переписываются — они **оборачиваются** в плагины.
Растворяются ровно 917 строк `createSlotGame`, а не двадцать тысяч рабочего кода.

```ts
// БЫЛО — ~25 именованных полей, ветки stake/artube/shell/loading внутри хоста
createSlotGame({ model, normalize, scenes, manifest, design, scaleMode, fonts,
                 stake: { adapter }, artube: { load }, shell: {...}, loading: {...},
                 shellFactory, bonus, skipGesture, audio, pixi, ... })

// СТАЛО
runGame({ project: './project.json' })
```

Игра больше не импортирует ни stake, ни artube, ни shell. Всё это — состав плагинов в
`project.json`, то есть переключатели в IDE.

### 7.1 Точки расширения Среза 0

| Точка | Фаза | Арность | Кто заполняет |
|---|---|---|---|
| `renderer` | runtime | one | `renderer-pixi` |
| `boot.overlay` | runtime | one | `loader`; artube подменяет своим через тот же матчер активации |
| `ui.shell` | runtime | one | `shell-html` |
| `session.provider` | runtime | one | `session-dev` / `session-stake` / `session-artube` |
| `build.target` | build | many | те же три, vite-сторона |
| `reel.feature` | runtime | many | `reel-system` — 13 встроенных фич как обычные контрибуции |

`scene.node`, `flow.step`, `anim.clip`, `asset.pipe`, `editor.panel`, `editor.inspector`
объявятся своими спеками (M5–M7). **Ядро для этого трогать не придётся** — ради этого и выбран
открытый реестр.

### 7.2 Два места, где модель проверяется, а не декларируется

**Reel-фичи.** Сегодня `FEATURES: Record<FeatureKey, ReelFeature>` — закрытая запись; чужую
фичу добавить нельзя вообще. Плагин `reel-system` объявляет точку `reel.feature` и кладёт туда
те же 13. Четырнадцатая, чужая, встаёт рядом без правки движка. Это одновременно и проверка
модели: **если 13 реальных фич не лезут в схему точки — модель неверна**, и мы узнаем это на
первой неделе.

**Выбор провайдера сессии.** Точка `arity: 'one'`, кандидатов трое. Контрибуция объявляет
**декларативный матчер**: `{ urlParam: 'sessionId' }` для artube, `{ buildTarget: 'stake' }`,
`{ default: true }` для dev. Ядро вычисляет активного; ноль или двое — диагностика с
человеческим текстом. Это выносит наружу `classifyArtubeLaunch`, спрятанный сейчас внутри
хоста, и позволяет IDE **показать**, при каком запуске что включится. Для действительно
сложных случаев есть `match()`-функция — но объявленная в манифесте.

## 8. §4 — Оболочка IDE

### 8.1 Почему v1 ощущалась отладчиком

1. **Вход был из игры, а не в игру.** Проект создавал CLI, IDE прицеплялась сбоку.
2. **Она не покрывала работу целиком.** Математика, звук, сборка, публикация жили в терминале.
3. **В ней ничего не *настраивалось*.** Правка свойств узла — не настройка игры. Ощущение
   среды даёт возможность **собрать игру из частей**, а её как раз и не было.

Экраны Среза 0 лечат ровно эти три причины, и ничего сверх.

### 8.2 Экраны

- **Воркспейс.** Первое, что видишь, — твои игры. «Новый проект» из шаблона живёт здесь;
  `create-slot` становится тонкой обёрткой над той же операцией.
- **Состав** (сердце среза). Установленные плагины, включение, **настройки, отрисованные из
  схем**. Тут же: кто какие точки объявил, кто во что контрибуцирует, **при каком запуске какой
  `session.provider` включится**, диагностики резолюции. Локальный каталог доступных плагинов —
  предтеча маркетплейса, тот же экран.
- **Превью.** Игра в iframe, **несколько экранов одновременно** (пресеты устройств, ориентации,
  языки — `SCREEN_PRESETS` и `LANGS` уже лежат в `harness`). Стена, а не одна рамка с зумом.
- **Код.** Monaco для `plugins/**` и `game/script.spin`, с ошибками от `e8 check` в редакторе.
- **Ассеты.** Дерево, CRUD, загрузка. Без перетаскивания на канвас — канваса-редактора в этом
  срезе ещё нет.

**Не входит в Срез 0** (говорится вслух): редактор сцен, flow-канвас, анимации, пошаговый
дебаг. Это M5–M8.

### 8.3 Мост IDE ↔ игра

**Мост сам становится плагином** фазы `editor`. В продовой сборке его просто нет. Сейчас в игру
приходится вписывать `mountIdeBridge` руками — это исчезает.

Протокол — `postMessage` RPC (в v1 работал), но контракт пересобирается под `ResolvedPlan`:
снапшот плана, изменение настроек, перезагрузка, диагностики.

## 9. Обработка ошибок

Единый принцип: **отказ — это данные, доходящие до человека.**

| Уровень | Поведение |
|---|---|
| Резолюция плана | `{ plan, diagnostics[] }`, не исключение. `error` — игра не стартует, показывает экран с текстом; `warning` — стартует деградировав. |
| Валидация настроек по схеме | Диагностика с путём поля и ожидаемым типом; значение падает на `defaults`. |
| Конфликт `arity: 'one'` | Ноль кандидатов или двое — `error` с перечислением кандидатов и их матчеров. |
| Цикл в `dependsOn` | `error` с печатью цикла. |
| Несовпадение `engine` range | `error` с обеими версиями и подсказкой. |
| Ошибка `create()` в рантайме | Изолируется: контрибуция помечается сбойной, остальные живут; в IDE — красная строка. |
| Ошибки `e8 check` | В Monaco как маркеры, в панели диагностик — списком. |

## 10. Стратегия проверки

Два уровня, оба обязательны.

**Юнит (Vitest, без браузера и без pixi):** резолюция, топосортировка, слияние схем точки и
контрибуции, валидация значений, матчеры активации, диагностики, парсер `.spin` → `SpinSchema`.
Всё это — чистые функции над данными; ядро не импортирует ничего тяжёлого, и это проверяется
отдельным тестом.

**Headless-петля (puppeteer, скриншоты + ассерты):** «игра действительно грузится и играется».
Три урока v1, которые встраиваются в петлю с самого начала:

- анимацию и загрузку **нельзя** проверять глазами в браузере — свёрнутая или перекрытая панель
  душит `rAF` в ноль, и проверка врёт;
- в headless-puppeteer **Pixi не получает pointer-события** — любые проверки канваса гнать через
  RPC, а мышь смотреть только в реальном браузере;
- пикинг вешать на DOM-канвас, а не на Pixi stage.

## 11. Критерии приёмки Среза 0

Срез сдан, если выполнены все пять:

1. Копия `moon-spice-market` грузится и играется через `runGame({ project })`; в коде игры ноль
   именованных веток `stake`/`artube`/`shell`.
2. В IDE, **не открыв ни одного файла**, можно выключить reel-фичу, поменять её настройки,
   подменить shell и переключить провайдера сессии на stake — и увидеть это в превью.
3. Чужая четырнадцатая reel-фича, лежащая в `plugins/` проекта, появляется в списке и работает
   **без единой правки движка**.
4. Битый проект даёт список понятных диагностик, а не белый экран.
5. Headless-петля со скриншотами проходит целиком: загрузка, спин, вход и выход из бонуса.

Пункты 2 и 3 — ответ на «это IDE, а не отладчик». Остальное — гигиена.

**Фазы реализации** (детализирует план): ядро и его тесты → шесть плагинов и перенос копии
игры → формат проекта и парсер `.spin` → приложение IDE. Первые три фазы проверяемы без
единой строки UI; четвёртая — то, что решает судьбу.

## 13. Риски и открытые места

| Риск | Смягчение |
|---|---|
| 13 реальных reel-фич не лезут в единую схему точки | Проверяется первым делом в M2 — до того, как на модели построено что-то ещё. |

| Копия `moon-spice-market` разойдётся с оригиналом | Оригинал read-only; движок подключается `file:`-симлинком с `resolve.dedupe` для `pixi.js` (двойной pixi ломает типы и Assets — урок v1). |
| Параллельные rollup-сборки забивают машину | Собирать `dist` строго по одному пакету за раз (урок v1: load 80–130). |
| «Состав» окажется скучной формой и снова не даст ощущения среды | Критерий 2 сформулирован как сценарий, а не как экран: проверяем поведением, а не скриншотом. |
| Скоуп `@energy8engine/*` требует новых npm-имён | Публикация новых пакетов — часть плана реализации; legacy-скоуп не трогаем. |
