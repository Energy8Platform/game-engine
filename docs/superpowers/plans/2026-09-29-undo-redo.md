# Undo and redo Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Mod+Z / Mod+Shift+Z / Mod+Y undo and redo the edits of the active tab (scenes, Flow, Symbols, Reels, Composition) and, with focus in the Explorer, its file operations.

**Architecture:** A client `history` service keeps steps per data key (`scene:<id>`, `flow`, `symbols`, `row:<id>`, `files`); each service records one step per accepted write (a value step: before/after + read/write through its own method); plugins declare which keys a tab undoes. A key router in `Shell.tsx` (and canvas pages forwarding their keys) runs undo/redo on the active tab's keys or on `files`; a status item shows the result.

**Tech Stack:** React 18, cordis 4, vitest + testing-library (`engine/ide/client`), scene-edit (`engine/game/scene-edit`), Playwright (`engine/apps/web`).

**Spec:** `docs/superpowers/specs/2026-09-29-undo-redo-design.md`

## Global Constraints

- `packages/*` is not edited. No `@energy8platform/game-engine` under `engine/`. Every change carries a test in its package.
- History is in memory only; 100 steps per key; a new step clears that key's redo branch.
- A step is recorded only for a write the host accepted (no `error` diagnostic); an undo/redo is never recorded.
- Before applying, the current value is compared (JSON) with the step's "after" (undo) / "before" (redo); a difference refuses, drops the step and says `changed elsewhere since — can't undo` (`… can't redo`).
- Keys: Mod+Z undo; Mod+Shift+Z and Mod+Y redo; skipped in `input`/`textarea`/`[contenteditable]`/inside `.monaco-editor`; focus inside the Explorer sidebar → `files`; else the active tab's keys.
- Explorer remove: over 20 MB (all bytes under the path) it is not undoable, and the confirm says so.
- Status line for 4 s: `Undo: <label>`, `Redo: <label>`, `nothing to undo`, `nothing to redo`, or the refusal.
- One workspace per test command; `@energy8engine/ide-host` ALONE. Playwright ALONE from `engine/apps/web`: `E8_E2E_HOST_PORT=5779 npx playwright test <files>`.

## Review Focus

1. **A person edits while an undo's write is still in flight** (a slow host): the new edit is recorded, and the undo's own write is not. Pinned in Task 1 (the replay guard is per write, not a global window — see Task 1's code).
2. **The echo frame of the person's own write arrives before the PUT answer** (the host broadcasts first): the step is still recorded with the doc the person wrote, and an immediate undo does not refuse as "changed elsewhere". Pinned in Task 2.
3. **Undo in the Composition tab of a row last edited in the Reels tab, then redo from Reels**: both work (the keys overlap). Pinned in Task 2.
4. **Mod+Z while typing in a SchemaForm number field or Monaco**: the field's own undo runs; the IDE history is untouched. Pinned in Task 3.
5. **Removing a folder in the Explorer and undoing it**: every file comes back with its bytes (binary included) and the tree is refreshed. Pinned in Task 5.

```ts
/** One undoable change: how to take it back and how to make it again. Each answers `null` when applied, or why not. */
export interface HistoryStep {
  label: string;
  undo(): Promise<string | null>;
  redo(): Promise<string | null>;
}
export type HistoryResult =
  | { kind: 'undo' | 'redo'; ok: true; label: string }
  | { kind: 'undo' | 'redo'; ok: false; reason: string };
export interface HistoryService {
  /** Adds a step under `key` (no-op for a write the history itself is making — see `replay`). */
  record(key: string, step: HistoryStep): void;
  undo(keys: readonly string[]): Promise<HistoryResult>;
  redo(keys: readonly string[]): Promise<HistoryResult>;
  /** Registers which data keys a tab undoes; the first matcher answering wins. Returns a disposer. */
  scope(match: (tabKey: string) => readonly string[] | undefined): () => void;
  keysFor(tabKey: string | undefined): readonly string[];
  /** Runs `write` with recording off for the writes it starts — used by value steps. */
  replay<T>(write: () => Promise<T>): Promise<T>;
  /** True while a `replay` write is in flight (services check it before recording). */
  replaying(): boolean;
  /** The last undo/redo result and when (ms), for the status line. */
  last(): { result: HistoryResult; at: number } | undefined;
  subscribe(listener: () => void): () => void;
}
/** A step over a whole value: compares the current value (JSON) before applying; writes through `write`. */
export function valueStep<T>(opts: {
  label: string;
  before: T;
  after: T;
  read(): T | undefined;
  write(value: T): Promise<{ error: string | null }>;
  history: HistoryService;
}): HistoryStep;
```

`ctx.history` is provided; `declare module 'cordis'` adds `history: HistoryService`.

- [ ] **Step 1: Failing tests** (`history.test.ts`, a plain cordis `Context` with the plugin):
  - record then `undo(['a'])` runs the step's `undo` and answers `{ ok: true, label }`; `redo(['a'])` runs `redo`; nothing recorded → `{ ok: false, reason: 'nothing to undo' }` / `'nothing to redo'`.
  - a new `record` on a key clears that key's redo branch (not other keys').
  - 101 records on one key → the first is gone (100 undos succeed, the 101st answers nothing to undo).
  - latest among keys: record on `a` then `b` then `a` → `undo(['a','b'])` takes the last `a`, then `b`, then the first `a`; `redo` replays in the reverse order.
  - a step whose `undo` answers a reason → the result is that reason, the step is dropped (a second `undo` goes to the previous step), and redo does not get it.
  - `valueStep`: undo with `read()` equal to `after` writes `before`; with `read()` different → no write, answer `changed elsewhere since — can't undo`; redo symmetric with `before`/`after` and `can't redo`; a `write` answering `{ error }` → that error is the reason.
  - Review Focus 1: while a `replay(write)` is pending, `replaying()` is true; `record` called from INSIDE the replayed write (same async chain) is ignored, and a `record` made after the replay settled is kept. (Implement the guard as a counter around the awaited write; document that an edit landing during a replay's await is the ceiling — `// ponytail:` note naming it.)
  - `scope`: two matchers, `keysFor` answers the first defined; a disposed matcher no longer answers; `keysFor(undefined)` → `[]`.
  - `last()` holds the latest result with a timestamp; `subscribe` fires on record/undo/redo.
- [ ] **Step 2:** `npm test -w @energy8engine/ide-client -- history` — FAIL.
- [ ] **Step 3: Implement.** Per key: `{ done: Entry[]; undone: Entry[] }` with `Entry = { seq: number; step: HistoryStep }`; a global `seq` counter. `undo(keys)`: pick the entry with the highest `seq` among the keys' `done` tops; pop it; run `step.undo()`; on `null` push it onto that key's `undone`; on a reason drop it. `redo` mirrors with `undone`. `valueStep` builds `undo`/`redo` from `read`/`write` with `JSON.stringify` comparisons and runs the write through `history.replay`.
- [ ] **Step 4:** `npm test -w @energy8engine/ide-client`, typecheck — PASS / 0.
- [ ] **Step 5: Commit** — `History: an undo/redo service with steps per data key, the latest among a tab's keys first`.

- [ ] **Step 1: Failing tests:**

  - move → undo moves back; refused when the old path now exists; redo moves again.

  - upload over an existing file → undo writes the previous bytes; upload of a new file → undo removes it.
